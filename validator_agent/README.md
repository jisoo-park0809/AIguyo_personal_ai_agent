# 학생 검증 agent

생성된 커리큘럼을 **학생 페르소나 4명이 각자 수강해 보고** 막히는 곳을 보고하면, 코드가 충실도 검사·집계·합격 판정을 하는 agent입니다.
통합 투표의 검증 기능 c6a(편성표만 보고 평가·반복 판정), c6c(페르소나 충실도 검사), c6d(위치·심각도·제안), c6f(페르소나 추가), c7a(점수 기반 합불)를 반영했어요.

## 실행

프로젝트 폴더(`Content_Agent`)에서:

```bash
# 생성 agent 결과를 검증 (OPENAI_API_KEY가 있으면 실제 AI, 없으면 시연용 정책)
.venv/bin/python -m validator_agent --curriculum generator_agent/output/sample_curriculum.json

# API 없이 시연 (비용 없음)
.venv/bin/python -m validator_agent --curriculum generator_agent/output/sample_curriculum.json --mock
```

`--request`는 과정·학습자 정보가 든 생성 agent 입력이에요(기본: `generator_agent/data/sample_input.json`). 비전공자 비율, 합격 기준, 예산 상한을 여기서 읽어요.

앱에서는 `.env`의 `AI_PROVIDER=pipeline`일 때 "학생 입장에서 검증하기"가 이 agent로 실행돼요(`app/ai/pipeline_provider.py`).

| 결과 파일 (`output/`) | 내용 |
|---|---|
| `<이름>_validation.json` | 판정, 페르소나별 점수, 경고, 보완점, 생성 agent 수정 모드용 `persona_feedback`, 앱 화면용 `app_validation` |
| `<이름>_validation.md` | 사람이 읽는 검증 결과 |
| `<이름>_validation_trace.json` | 페르소나별 수강 일지·보완점·tool 호출(고른 이유 포함) |

모델은 `VALIDATOR_MODEL` → `GENERATOR_MODEL` → `OPENAI_MODEL` 순으로 써요(지금은 gpt-5.4-mini).

## 흐름

```
① 학생용 보기 (views.py, 코드): 교육 목적·배분 이유·규정 메모·점검 결과는 지움 (p3)
② 학생 1~4(+ 운영자가 추가한 유형)가 각자 수강 (agent.py, AI, 병렬): tool로 교과목·퀴즈를 보고 → 수강 일지(퀴즈 난이도 포함) → 보완점 보고 → 점수 제출
③ 충실도 검사 (judge.py, 코드): 설정과 다르게 답한 실행은 빼고 한 번 다시 평가
④ 집계·판정 (judge.py, 코드): 점수 계산, 가중 평균, 합격 판정
⑤ 판정 횟수 조절: 가중 평균이 합격 기준 ±0.3 안쪽이면 다시 평가 (최대 3회차)
```

## 학생 페르소나 (`data/personas.json`)

| | 학생 1 | 학생 2 | 학생 3 | 학생 4 |
|---|---|---|---|---|
| 설명 | 지식·프로젝트 경험 있는 전공자 | 지식은 있으나 프로젝트 경험 적은 전공자 | 지식·경험은 있으나 전공자보다 약한 비전공자 | 지식·경험 없는 비전공자 |
| 이미 아는 것 | 기초 전부 | 기초 전부 | 기초 문법·도구 일부 | 없음 |
| 주로 따지는 것 | 반복·깊이 | 프로젝트 안내 | 기초 공백·진도 | 따라갈 수 있는지 |
| 하루 복습 | 1시간 | 2시간 | 2시간 | 3시간 |

카드를 고치거나 추가하면 바로 반영돼요(c6f). 앱의 "학생 입장에서 검증하기" 화면에서도 **학습자 유형을 추가**하고 검증할 학생을 고를 수 있어요(`data/learner_types.json`에 저장, `app/learner_types.py`). `group`(major / non_major)은 가중 평균에 쓰여요.

## tool 10개 (`tools.py`)

커리큘럼을 고치는 tool은 없어요. 모든 tool은 `why`(고른 이유)를 받아요.

| tool | 하는 일 | 내부 |
|---|---|---|
| `get_my_profile` | 내 페르소나 카드 | 데이터 |
| `view_course`, `view_subject` | 과정 개요, 교과목 상세 (학생용) | 코드 |
| `view_quiz` | 교과목 객관식 퀴즈 (문제와 보기만, 정답·해설은 뺌) | 코드 |
| `check_prerequisites` | 선수 지식 중 앞에서 안 배웠고 내가 모르는 것 | 코드 |
| `estimate_workload` | 그 주의 수업 시간·교과목 수·새 주제 수 vs 내 복습 시간 | 코드 |
| `compare_subjects` | 두 교과목의 주제 겹침 | 코드 |
| `write_journal` | 교과목별 이해도(상/중/하)·학습량·막힌 이유, 퀴즈가 있으면 **퀴즈 난이도(쉬움/적절/어려움)와 이유** (없으면 거부) | 기록 |
| `report_gap` | 위치·문제·이유·심각도·제안 (위치 없으면 거부) | 기록 |
| `finish` | 5개 항목 점수(1~5)와 수료 가능성 (모든 교과목 일지가 있어야 통과) | 코드 검사 |

## 판정 규칙 (`judge.py`)

| 항목 | 규칙 |
|---|---|
| 페르소나 점수 | (스스로 매긴 5개 항목 평균 + 일지 이해도 점수) ÷ 2. 이해도는 상=5, 중=3, 하=1 |
| 수료 가능성 | AI 답과 일지 기준 중 더 나쁜 쪽. 일지 기준: '하'가 60% 초과면 불가, 30% 초과면 위험 |
| 전체 점수 | 비전공자 비율 가중 평균 (예: 비전공 60% → 학생 3·4 각 30%, 학생 1·2 각 20%). 단순 평균도 함께 표시 |
| 합격 | 생성 단계 규정 점검 통과 + 수료 불가 학생 없음 + 가중 평균 ≥ 합격 기준(기본 3.1) |
| 충실도 | 모르는 선수 지식이 있는데 이해도 '상', 지식 없는 학생이 절반 넘게 '상', 경험 많은 학생이 절반 넘게 '하' → 실행 제외 후 1회 재평가, 그래도 안 되면 "판정 근거 부족" |
| 경고 | 수료 위험, 2점 이하 항목, 스스로 매긴 점수와 일지의 큰 차이, 학생 3명 이상이 '하'인 교과목, 학생 3명 이상이 '어려움'인 퀴즈, 모든 학생이 '쉬움'인 퀴즈(변별력 부족) |
| 퀴즈 충실도 | 이해도 '하'이거나 모르는 선수 지식이 있는데 퀴즈를 '쉬움'이라고 하면 설정과 다른 답으로 셈 |

**점수를 일지로 다시 계산하는 이유**: 첫 실제 시험에서 학생 4가 교과목 8개 중 7개를 '하'로 적고도 스스로 4점을 매겨, 학생 3명이 수료 위험인데 합격(4.08)이 나왔어요. 원칙 p1대로 코드가 일지를 함께 반영하니 불합격(3.48, 학생 4 수료 불가)이 됐어요.

## 시험 결과 (2026-11-10, gpt-5.4-mini)

| 시험 | 결과 |
|---|---|
| 생성 agent 예시 결과 검증 (CLI) | 49초 · 약 176원 · 불합격 3.48 (학생 4 수료 불가) · 결과: `output/sample_validation.md` |
| 앱 경로: 생성 → 검증 | 생성 39초 · 약 44원 / 검증 48초 · 불합격 2.37 (모듈 7개 과정이라 학생들이 많이 막힘) |
| 시연 정책 (앱 화면) | 생성 → 저장 → 자료실 → 검증 → 결과 화면까지 오류 없음 |
| 앱 함수로 생성 → 말로 수정 → 검증 → 보완점 반영 | 생성 56초·62원 / 수정 13초·14원 (S01만 고침) / 검증 212초·586원 (2.9점이 기준 근처라 3회차까지 + 학생 4 재평가, 불합격 2.91) / 반영 11초·13원 (고른 보완점의 S05·S08만 고침) |

퀴즈 검증을 넣은 뒤(2026-11-11, gpt-5.4-mini) 같은 커리큘럼: 3회차 · 273초 · 약 945원 · 불합격 3.0. 퀴즈를 보느라 학생마다 단계가 늘어 회차당 비용이 약 300원으로 올랐어요.

판정 횟수를 늘리면 시간과 비용이 회차 수만큼 늘어요(1회차 약 1분·약 180원). OpenAI 요청은 2분 안에 응답이 없으면 다시 시도해요(`OPENAI_TIMEOUT`).
